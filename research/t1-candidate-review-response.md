# Assessment of the independent T1 candidate review

Date: 2026-10-03. **Status: review assessment and proposed priorities; no runtime fixes applied.** This responds to the [independent review](t1-candidate-independent-review.md) at `fed8c96`. Rust/build inputs still match candidate `3422c7b`; subsequent changes through that head are documentation and research. Publication remains deferred. Probes used archived source and disposable private state, never the owner's running daemons.

## Conclusion

The review identifies substantial defects. The passing T1 workflow and the newly recorded two-Mac enrollment, join, sealed note and assignment-readiness checks remain useful evidence; they do not exercise the authorization and failure paths described here. The two-Mac run stopped before claim/submission and does not establish task completion, restart or sleep/wake.

I agree with the main confidentiality, admission, screening, content-recovery, backpressure and durability findings. I would address these before adding the production MCP bridge. In particular, IR-1/2/3/14 are authorization or confidentiality failures even though the literal T1 guide avoids them. The review's severity scale deliberately depends on that guide; it should not determine readiness for multiple principals, viewers or coding clients.

This is not blanket acceptance of all wording or suggested fixes. IR-5 is a protocol-policy consequence, some consequences are overstated, some performance numbers are extrapolations, and the retained store verifier has a concrete reproducibility defect.

## Fork policy: agree with the problem, not an arrival-dependent fix

**IR-5 reproduces:** accepted heads `[100, 101, 102]` become `[100]` after a member fork excludes a dependency. This follows the existing rule in the [fold](../crates/locust-core/src/goal/fold.rs); it is not an accidental deviation from the contract.

Protecting an event because a decision was *previously applied on this replica* would break convergence. One replica receives proposal X, assignment D, then conflicting X'; another receives X and X' before D. If only previously applied D is protected, the same held event set produces different outcomes. That violates the [contract's arrival-order rule](../docs/protocol-v0.md).

If acceptance is to survive later member equivocation, branch selection must instead be derived from the canonical coordinator decision chain and its exact references, including transitive semantic dependencies. The policy must specify competing references and preserve membership, epoch, removal and transition checks. That is a protocol change requiring permutation, incremental-fold and replay tests. The retained patches demonstrate the current issue; they do not implement or validate this replacement. Keeping conservative invalidation and explicitly documenting revocable acceptance is also a coherent policy, with a product tradeoff.

**IR-6 wording needs narrowing.** The earlier replica is not unaffected: its proposal is already fork-excluded and the assignment fails its precondition. It nevertheless advances past the assignment and applies the later admission. The late replica cannot advance because the dropped proposal remains a missing reference. The waiting-bound attack reproduces from an honest earlier holder alone. The variant-bound attack needs other variants to fill the quota first; that holder alone serves at most its retained 16 variants, including the required proposal, and converges in the control case.

## Durability evidence needs two distinctions

First, the matching original [store probes](evidence/t1-candidate-review/store.patch) and [flush interposer](evidence/t1-candidate-review/store-flush-interposer.c) do reproduce the observations:

- IR-9: the writer exits 77 at B's WAL flush; reopening returns positions `[1, 2]` without an explicit WAL flush before reads. Garbage collection also acts on recovered B's deletion. This demonstrates a missing recovery barrier; actual power-loss disappearance and a distributed author fork were not observed.
- IR-32: after an injected final staging-flush failure and reopen, finishing 2 MiB returns `Ok(true)` without a fresh staged/object-file flush. Poisoning only the original handle is insufficient.
- IR-33: a pre-commit row-insert failure occurs after the staged file is renamed, consumes the recoverable staging and makes retry return `Ok(false)`. This violates the pre-commit “nothing applied” rule. A commit-time WAL failure alone has an explicitly unknown outcome and is weaker evidence.
- IR-34: stage/discard retry paths can skip an uncertain directory flush. Recovery must repair this too.

Recovery must establish durability under exclusive ownership before serving recovered state or deleting objects based on it. SQLite may internally read recovery data before that barrier; the report's literal “before the first read” is stronger than necessary. For promotion, preserve recoverable staging until the database decision is durable. A compensating rename or truncate is not automatically safe because it can fail as well. These are repair requirements, not implemented fixes. SQLite's [WAL documentation](https://sqlite.org/wal.html) distinguishes readable commit records from synchronization/checkpoint durability.

Second, **the retained independent verifier is mismatched with the retained interposer**. [verify-store.patch](evidence/t1-candidate-review/verify-store.patch) uses `PROBE_TRACE`, `PROBE_FAIL_SUB`, `PROBE_KILL_SUB` and arm-file variables. The provided C helper recognizes `LRC_TRACE`, `LRC_FAIL` and `LRC_DIE` instead. Running them together unchanged reports six passing tests, but the supposedly killed writer exits 0, failed staging succeeds, and failed promotion returns `Ok(true)`. Most tests print rather than assert the injection outcome. This does not refute the findings demonstrated by the matching original probes; it limits the reproducibility of the claimed second confirmation. Preserve the actual matching verifier helper and assert every injected fault fired.

## Build, environment and evidence claims

The Python requirement is real: `build_t1.py` imports `tomllib` and uses `hashlib.file_digest`. This session's `python3` is 3.14.6 and imports it; `/usr/bin/python3` is 3.9.6 and fails immediately with `ModuleNotFoundError`. The review's Python 3.10 observation describes its environment, not a universal current interpreter. Document or check Python 3.11+; do not invalidate the earlier 63-test success on a newer interpreter.

The build helper inherits its environment and checks compiler identity separately from the actual build. Environment/index-flag/reproducible-path concerns deserve a dedicated build audit, but the earlier-review rows explicitly say they were not rechecked at the candidate. Likewise, configuration collisions, shared client session files and lifecycle-harness shortcuts remain audit leads, not newly reproduced candidate defects in this assessment.

The macOS local-network-permission explanation remains a hypothesis. Selected relay routes and multicast `No route to host` do not identify the cause, and the current daemon logs a path snapshot at connection establishment rather than current paths continuously. The evidence's mixed timestamps and absolute local paths are record-quality issues; they do not establish runtime corruption or leaked credential bytes.

## Proposed order

1. Fix principal read isolation and invitation/admission authorization (IR-1/2/3/4/14), with rejected-join and removed-member regressions over every read surface.
2. Fix screening liveness, poisoned staging and durability/promotion recovery (IR-6/7/9/32/33/34); make fault injection self-checking.
3. Fix exchange backpressure, one-way idle detection, failed-node shutdown and unadmitted connection retention (IR-8/16/22/23/24).
4. Decide fork finality explicitly (IR-5), then cover the chosen rule with the retained permutation/replay harness. Fix accepted-result presentation and halt-proof delivery without widening authorization.
5. Finish join/revocation/CLI recovery and smaller protocol/performance/documentation issues, rerun the affected local workflows and continue the physical-machine tests. MCP/client integration then builds on corrected boundaries.

These are recommendations for the next implementation scope, not a claim that the fixes have landed or that any remaining release gate has passed.
