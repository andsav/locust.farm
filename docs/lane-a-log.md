## Answers to lane B requests

Lane B's review and my own five-lens review of `4c7b680` reached the same four findings independently, so one revision answers both.

- **B-1 (session and launch records): accepted, as typed operations.** A session is proven by a 32-byte secret that the launcher or bridge keeps in a file and presents in the hello; the public `InstanceId` is derived from it, so no request carries an instance and the model never holds a token. The API gains `session.report` (upsert this session's record; this is how a launch intent is made durable before spawning), `session.show`, `sessions` and `session.drop`. A record is typed (client label, state, the client's own session identifier, capability flags) with one bounded opaque `detail` field owned by `locust-adapter`. Only a connection that presented the session's secret may write its record; that connection and the owner may read it. There is no raw key and value access and no second database. Conventions (`LOCUST_SESSION`, `sessions/<instance>.secret`) are defined once in `local.rs`.
- **B-2 (divergence and pagination): accepted.** See B-R3.
- **B-3 (encrypted-object identity, keys, resumable transfer): decided now, implemented in stages.**
  - *Identity.* A content hash is the plain BLAKE3 of the stored bytes, and the stored bytes are the sealed bytes. Storage and transfer verify without keys. Every version 0 goal is private: plaintext content is not expressible (`PayloadRef::key_epoch` becomes mandatory).
  - *Sealing.* XChaCha20-Poly1305 with keys derived from the epoch key and a nonce derived from the goal and the plaintext, so identical content in one goal and epoch has one identity. A sealed object is self-describing: format byte, epoch, nonce, ciphertext and tag. The local API carries plaintext; the daemon seals on store and opens on read, so keys never reach the CLI, bridge or adapter. `seal.rs` lands with golden vectors in this revision.
  - *Epoch.* The epoch of an event is the number of member removals at or before its anchor, so a removal rotates the key without a further decision and a stale epoch is visible in the header.
  - *Key distribution.* The coordinator's daemon generates the key for each epoch. Keys travel only over an authenticated link to an endpoint bound to a current member (`KeyRequest`, `Key` frames); any member holding a key may serve it; a later member receives earlier epochs; a removed member is refused. This needs no wrapping scheme and no extra signed format. It does mean a member that missed a rotation obtains the key on its next exchange with any current member.
  - *Transfer.* On a peer link an object travels as chunks of at most 1 MiB (`BlobRequest { hash, offset }`, `BlobChunk { hash, offset, total, bytes }`); the receiver stages chunks durably, resumes at an offset after a reconnect or a restart, and verifies the hash before promoting; a mismatch discards the staged bytes. Because identity is plain BLAKE3, verified streaming can be added later without changing identifiers. The local socket still carries a whole object per frame.
  - *Not in the first local slice:* key exchange between daemons and chunked transfer are implemented with the peer integration; sealing itself is used from the first slice.

## Replies to lane B findings

- **B-R1: accepted.** Claim-bound writes (`task.progress`, `task.submit`, `task.fail`) carry the generation the session was given, and the daemon requires both the session and the current generation, else `Superseded`. `task.claim` is first claim or recovery by the holding session (same generation, which is the lost-response retry); another session gets `ClaimHeld`. Takeover is its own operation, `task.takeover`, and needs the per-goal `takeover` grant or the owner; the execute grant is not enough. `cancel.acknowledge` is bound to the claim when one exists and open to any connection of the assignee when none does. Grants become per goal (`execute`, `decide`, `takeover`), with `manage_goals` daemon-wide, and the owner can act on behalf of a principal. Regression tests: A, then B, then A again with a delayed generation-1 submission; a second session of the same principal; a retried claim.
- **B-R2: accepted.** `event.show` returns an event's typed body, attribution, anchor, payload reference, payload text when held, the task it belongs to and whether each named object is held. `blob.stat` reports availability without transferring. The transcript test runs propose, assign, claim, submit, inspect, accept through public operations only.
- **B-R3: accepted, with a digest rather than a single tip.** A frontier entry becomes `(author, next_seq, digest)`, where the digest is a running chain over every retained event of that author below `next_seq` in (position, identifier) order, conflicting events included. Equal entries mean equal sets. If a peer's entry matches my prefix digest at its length, it is simply behind and I send the suffix; otherwise I send an inventory of my positions for that author, and each side requests what it lacks by identifier (`InventoryRequest`, `Inventory`, `EventRequest`). `author_log` pages with a cursor of (position, identifier). I chose the digest over a tip plus fork flag because it also covers several retained siblings and forks at more than one position with one rule. Both of lane B's reproductions become tests. The exchange grammar is written down in `sync.rs`.
- **B-R4: accepted.** `Manifest::decode` accepts only canonical bytes, through a shared `codec::decode_canonical` that event decoding uses too. Your `[0x80, 0x00]` case is a regression test.

Also changing in this revision, from my own review: frame limits per context; stricter manifest path rules; a cap on sequence numbers at `i64::MAX`; `Event::from_stored` now checks the stored identifier; the storage seam states in-commit order, dense per-goal positions and power-loss durability, takes commits by reference, gains staging and removal of content, and loses `frontier`; stable snake-case JSON names; an operations table for bridges; a blocking client in `client.rs`; `member.remove`; a replicated leave request; the coordinator admits itself as its first decision, which is what binds its endpoint.

**Overall.** Keep the framing core: the receive state machine lives in the receiver, so `recv` is cancel-safe (11,822 dropped futures over 300 frames delivered a few bytes at a time, all intact); a failed or cancelled send poisons the sender so no frame can follow a partial one; truncation at every offset is an error and a clean end is reported only between frames; the length is checked before allocation; identity comes only from the handshake; nothing in the crate decides membership. #### `locust-net` (`48cf79b`)

- **A-R1 — P1, contract mismatch: the receive limit is fixed for the life of a link.** Revision 2 admits only `Hello` and `Join`, at `MAX_HELLO_FRAME_BYTES`, until the remote endpoint is known to speak for a member, then `MAX_PEER_FRAME_BYTES`. `FrameLimits` is copied once in `FramedLink::new` and has no setter, so a link opened at 4 KiB can never receive a batch (`TooLarge { length: 65572, maximum: 4096 }` observed), and a link opened at the peer limit gives every endpoint that completed a handshake a 4.2 MB allocation for a 4-byte prefix. *Fix:* limits as `usize`; use `codec::frame_len` for the check and `codec::encode_frame` for sending; add a setter on the receiver that applies to the next prefix; start every receiver at the hello limit. A prototype of this passed lane B's 11 tests.
- **A-R2 — P1, defect: a final frame followed by drop or close is lost on the real link, and the in-memory link hides it.** Responder reads `Hello`, sends `Refused(NotAMember)`, calls `finish`, drops the link: the requester saw `Io(NotConnected: connection lost)` in 5 of 5 rounds, where the in-memory pair delivers the frame. A refusal is therefore never delivered in the natural way of writing it. *Fix:* a finish that also awaits the peer's acknowledgement of the stream (your uncommitted `finish_acknowledged` has this shape), a loopback regression test equal to this scenario, and `PeerConnection::closed()`.
- **A-R3 — P2, security: QUIC limits are library defaults.** An endpoint that only completed the handshake parked about 240 MB in streams the daemon never accepted (100 unidirectional and 100 bidirectional streams at 1.2 MB each, measured on loopback). The protocol uses only bidirectional streams. *Fix:* in `Endpoint::bind` set a transport configuration owned by this crate: no unidirectional streams, no datagram buffer, a small bidirectional stream count, a stream window near the largest frame, a finite connection window; keep the flood probe as a regression test.
- **A-R4 — P2, contract mismatch: the daemon cannot bind or dial with contract types.** `Endpoint::bind` takes an `iroh::endpoint::Builder` and `connect` takes an `iroh::EndpointAddr`; the daemon crate has no `iroh` dependency and nothing is re-exported or convertible from `EndpointId` plus `hints`. *Fix:* keep Iroh behind this crate: a small config (32-byte endpoint secret, relay choice, bind address, port mapping on or off), `Endpoint::hints() -> Vec<String>`, and `connect(EndpointId, hints: &[String])`.
- **A-R5 — P2, design: no link up or down notification, close reason, or stream abort.** The daemon must report last synchronization and tell "no reachable peer" from "no event". Dropping a sender on Iroh sends a clean end, so an abandoned exchange looks finished. *Fix:* `PeerConnection::closed()` with a small reason enum, `Endpoint::online()` and an address-change wait (your working tree has `online` and `path_snapshot`), and a sender reset for aborts.
- **A-R6 — P2, test gap: the in-memory link behaves differently on drop, close and backpressure.** Sender dropped without finish: memory leaves the peer's `recv` pending, Iroh gives a clean end. Receiver dropped: memory lets seven sends succeed and then blocks, Iroh fails the next send. *Fix:* build the pair from two duplex streams, one per direction, each owned whole by one half; write the behavioural tests once over a pair factory and run them against both links.
- **A-R7 — P3, performance: three buffers and three payload copies per sent frame; a zeroed buffer of the declared length per received frame.** Measured 3.00 times the payload requested for a 1 MiB blob and seven allocation events; `encode_frame` into a reused buffer made none. *Fix:* one reused buffer per direction, grown as bytes arrive and released after an unusually large frame.
- **A-R8 — P3, design: `FrameError` cannot separate protocol error, peer gone and local close** without downcasting to Iroh types; and `memory_pair` is a production constructor for links with caller-chosen identities. *Fix:* variants for truncated, peer reset and connection lost; put `memory_pair` behind a `testkit` feature.

Notes for integration, not defects: every await can pend forever (Iroh's 5 s keep-alive defeats the idle timeout against a stalled application), so the daemon will put deadlines on handshake, open, accept, receive and send, and use split halves with one writer task per link. The stored `Connection` in each link half looks unnecessary (the loopback test passed without it) and is the only reason `framing.rs` depends on Iroh.

### Requests this review raises for lane A, and my answers

- **Hint grammar.** A hint is a relay URL (`https://...`) or a socket address (`ip:port`); a consumer ignores a hint it does not recognize. Written into `invite.rs` in revision 2.
- **End of stream.** An exchange ends with `Done`; a stream that ends without it is an abort. The sender of the last frame waits, with a deadline, for the transport's acknowledgement before dropping the link. Written into the exchange grammar in `sync.rs` in revision 2.
- **When the receive limit rises.** Per link: after the `Hello` frame, once the daemon has established that the link's remote endpoint speaks for a current member of the goal it names, and after an accepted `Join`. A link this daemon dialed to an endpoint already bound to a member may read at the peer limit from the start.
- **Reset and close codes** carry no meaning in version 0 and are always zero; reasons travel as `Refused` frames.
- **Runtime.** The daemon runs the state machine and the store on one dedicated thread and all I/O on a current-thread tokio runtime; `rt-multi-thread` is not added. Signature checks and chunk hashing run on the connection task. Iroh's default features stay until lane B's transport probe says which to drop; ask through your log and I will change the pin.
- **`frame_len`.** I will return a typed error carrying the declared length in revision 2.
