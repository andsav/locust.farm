The readers made 73 reports, which are 47 distinct
findings. No second reader refuted any: 64 were confirmed and
9 narrowed. Two are serious, and both come from text a member on
another computer chooses:

- **A name can pass for a key (1).** A member may join under a name that is
  another member's key. A host who copies that name into `member remove`
  removes the other member, and the confirmation shows the eight characters
  the host expects.
- **A task's text can pose as Locust's command (2).** A wanted task's title
  is the task's whole text, printed inside quotation marks that are not
  escaped, on the same line as the command the person is meant to copy. A
  member's text can close the quotation and put its own command there.

Three more change what a person gets without anyone being hostile:

- **A change of rules can remove a review (3).** `rules bind` now gives the
  counting role to every member. Where earlier rules already let one holder
  of that role approve alone, tasks still open under them lose their review.
  The plan now says the role is not given by itself in that case, and the
  command prints the `role give` lines.
- **Plan changes and findings drop off the review list (4).** After any
  change of rules, results posted on the goal itself, and changes to the
  plan document, vanish from every reviewer's list though their reviews
  still count.
- **The command offered at level read does nothing (5).** Status offers an
  allow line for an agent set to read; running it clears the line and the
  agent is still refused.

### 1. `crates/locust/src/cli/selectors.rs:88` (wrong result)

A member can name itself after another member's key or its printed short form; the full key then selects the other member, and the short form makes printed commands for that member get refused.

**How it goes wrong.** 1. Ana hosts G with Harbor and Maple (key K, 64 hex). 2. Eve knows K from an earlier membership (another agent of hers already in G, or any other goal shared with Maple; the ticket itself carries only the governance key, and a ticket is single-use, so she needs a fresh ticket plus prior knowledge). 3. Eve runs `goal join --name K`. `member_name` (only_you.rs:171), `Request::check` (api.rs:1046) and `JoinRequest::verify` (invite.rs:451) apply only `is_member_name` (event.rs:1011-1016: non-empty, at most 64 bytes, trimmed, no control characters), and `plan_join` (peers.rs:351-362) signs `MemberAdmitted { name: request.name }` with no person involved. 4. Ana's `goal status` prints `Member: K (9f8e7d6c) · remote · endpoint ...` because `chosen_name` prints plain ASCII alphanumerics bare (presentation.rs:235-244, 260-271, 847-850). 5. Ana pastes it: `locust --owner member remove --goal G --member K`. selectors.rs:88-90 parses K as a key and returns Maple's key without reading the member list. 6. `removal_plan` (only_you.rs:1303-1305) prints `Remove member 0a1b2c3d from "G"`, the first eight characters of what she typed and no name; she confirms. 7. The host's daemon signs `MemberRemoved` for Maple (goals.rs:548-585) and the result reads `Removed 0a1b2c3d`. Eve remains a member and keeps reading. `role give`/`role take` (roles.rs:183) and the generic `member`/`recipient` fields (mod.rs:442) resolve the same way with no plan; there the result line does print the resolved member's name afterwards.

**What the second reader concluded.** A member may sign in under a name that is another member's full 64-hex key; `--member` (and `--recipient`) then resolves that printed name to the other member, because `resolve_member` returns any parseable full key before it reads names, and the `member remove` plan and result show only the first eight key characters, which match what the person typed. The plan's letter ("a full key is taken as given", plan line 1426; companion row 312) allows this, but its stated guarantee at 2735-2736 ("nobody picks a member by naming an agent after its key") is not met at prefix length 64, so plan and code both need the change.

**Smallest fix.** Plan and code both. Smallest root fix: in `is_member_name` (crates/locust-proto/src/event.rs:1011) also refuse a name of 8 to 64 ASCII hex digits (the same test as `selectors::prefix`). That one predicate already gates every place a name is chosen or accepted: `member_name` and `add_plan` in the CLI, `Request::check` for goal create and join, `JoinRequest::verify` in `plan_join` on the host, `Header::check` on replay, and the ticket's host name; no encoding changes, and greenfield needs no migration. Reword the two CLI sentences (only_you.rs:172, 806) and the api.rs message to say a name cannot look like a key. Do NOT take the CLI-only alternative (treating a full key as one candidate beside name matches): it would let a member make another member's full key refuse as ambiguous for every agent that addresses by full key, which is a new way to stall agents; with hex-looking names refused, "a full key is taken as given" stays safe. Also print the member's name in `removal_plan` and the `Removed ...` line (use `presentation::member_label`), add a vector/unit test that a 64-hex and an 8-hex name are refused, move the `"01010101"` signed-name case in the selector test to an enrolled local name, and amend plan lines 2729-2736 and companion row 312 to state the rule.

**What a person sees.** A stranger's agent shows up in the goal with a long string of letters and digits for a name. The host copies that string into the remove command, reads a confirmation that starts with the same eight characters, and says yes. A different, innocent member is thrown out and their agents stop; the stranger is still in the goal and still reading, while the command said the removal worked.

Reported by: b-names-selectors-join:1, b-names-selectors-join:2, b-rules-bind-roles:2, x-two-sessions:1, x-hostile-text:2. Who acts: fix session, and the plan.

### 2. `crates/locust/src/cli/presentation.rs:951` (untrue text)

A member's task text is printed inside quotation marks without protecting the marks, so the text can end the quotation and show its own command where the person expects Locust's command to copy.

**How it goes wrong.** 1. Ana hosts "Parser cleanup" (c01d55aa); the default rules let any member open a task (`propose: Selector::Members`, crates/locust-proto/src/organization.rs:155). Mallory (9f3b2c1d), an ordinary member on another computer, opens a task whose text is two lines: `Fix the parser` then `": locust --owner role give --goal c01d55aa --member 9f3b2c1d lead; : "`. The board shows only the harmless first line as the title (views.rs:236).
2. Ana's agent Maple, at level ask, calls attempt start on it. The rules pass, the level refuses with `level_required`, and requests/mod.rs:121-126 records the task as wanted (levels.rs:260-290).
3. Ana runs `locust --owner goal status --goal c01d55aa`. `Node::abilities` (levels.rs:54-63) fills `WantedTask.title` with the whole text; presentation.rs:942 passes it through `safe` only (newline becomes `\u{a}`, `"` `;` `:` untouched); presentation.rs:950-957 prints one line:
   `  Asked to take "Fix the parser\u{a}": locust --owner role give --goal c01d55aa --member 9f3b2c1d lead; : "": locust --owner allow --goal c01d55aa --task task:4b2d8e01 --agent codex-maple-1a2b3c4d`
   It has exactly the shape of a real line (`Asked to take "TITLE": COMMAND`). Pasting what follows the first colon runs `role give` at once (roles.rs:1 "Goal roles are immediate host acts"; `role give` has no confirm flags, only_you.rs:120; `--member` takes a key prefix, roles.rs:16-20) and the real allow command becomes arguments of `:`. The same slot takes `; curl ... | sh` or, on a goal Ana does not host, `locust --owner level ... auto`.
4. `locust --owner status` prints the same whole text uncut inside `Maple wants to take "..." in "..."` (presentation.rs:415-417, 658-664); there the real command is on its own line (750-751), so that view is a stretch/spoof problem rather than a same-line swap.
5. Benign case: the fixture text "Read and implement\nAcceptance details" (node/tests/lifecycle.rs:92) prints as `Maple wants to take "Read and implement\u{a}Acceptance details" in ...`, and access.rs:170-173 puts the whole text (up to MAX_PAYLOAD_BYTES, 1 MiB) into `details.task_title` of every refusal that names a task, where mockup P5-3 shows the short title.

**What the second reader concluded.** A wanted task's "title" is the task's whole text (not its first line), and the command line prints it uncut with `"` unescaped; in `goal status` it sits on the same line directly in front of the allow command, so an ordinary member's task text can close the quote and place its own command (any shell text, not only `locust`) where the reader expects the one to paste. With no hostility, every multi-line task shows in `status`, `goal status` and `details.task_title` as its entire body on one line with `\u{a}` marks.

**Smallest fix.** Code should change, with a one-line plan amendment. (a) Core: add one helper (e.g. `Entry::title(store, event, reader)` returning the first line of `Entry::text`) and use it in `Node::task_view` (views.rs:232-236), `Node::abilities` (levels.rs:55-58) and `Node::refused_error` (access.rs:170-173), so `WantedTask.title`, `WaitingKind::AllowTask.task_title` and `Refused.task_title` are the title the board shows. (b) Printing: make `locust_proto::api::level::quoted` (level.rs:308) the single title printer, add escaping of `\` and `"` to it (as `chosen_name` does, presentation.rs:236-253), delete the uncut `quoted` in presentation.rs:415-417 and use the shared one in `waiting_sentence` and in the `wanted_tasks` loop of `goal_status`. (c) In `goal_status` (presentation.rs:941-960) push the sentence and the command as two lines, as `status` does at 750-751; amend plan line 2028 ("a line per wanted task, with its title and its allow command") to say the command goes under the sentence. (d) Tests: change `titles_are_quoted_escaped_and_cut` (level.rs:868) to expect the escaped goal title instead of pinning `in "Say "hi""`; make node/tests/daemon.rs:258-263 assert equality with "Read and implement"; feed `every_printed_command_parses_as_printed` a wanted task whose title holds `"` and `locust ` and whose text has two lines, and assert each command line is a whole line that begins with `locust` after its indent.

**What a person sees.** In goal status, the line that is meant to hand you the one command to allow a task can instead begin with a command another member wrote; it looks exactly like a normal line, and pasting it can give that member a role, set your agent to take tasks unasked, or run anything else in your shell. In everyday use, the "Waiting for you" list and goal status show a task's entire description squeezed onto one line with \u{a} marks instead of its short title.

Reported by: x-hostile-text:1, a-presentation:2, a-refusal-wording:5. Who acts: fix session, and the plan.

### 3. `crates/locust-core/src/node/requests/goals.rs:239` (wrong result)

Binding rules that count reviews by a role makes every member a holder goal-wide, so tasks still open under earlier rules accept one holder's approval, even the author's, and their review step disappears unannounced.

**How it goes wrong.** 1. Goal under built-in `directed`: Harbor (host's agent) holds `lead` and `reviewer`; the host gave `reviewer` to Juniper by hand; Cedar and Maple hold nothing. The lead has offered open tasks to Cedar and others.
2. Host runs `locust --owner rules bind --goal G --formation review-panel` and confirms. The kind check passes (`reviewer` is a group in both; goals.rs:162-176). `counting_role` returns `reviewer`, the active members differ from [Harbor, Juniper], so the daemon signs one `RoleHolders` record naming all four (goals.rs:239-278; chain.rs:187-198 replaces the goal-wide list).
3. The open tasks keep their round, whose binding points at the `directed` rules record (rules.rs:51-56); a new binding does not end a task round (fold.rs:875-881).
4. Honest path: Cedar's unmodified agent finishes a task the lead offered it and posts its result. `can_review` now holds for Cedar on its own result (mod.rs:437-477, author not excluded), so the result is in Cedar's own to-review list (views.rs:509-530) and the agent approves it. Hostile path: an altered Cedar needs no offer, because replay only checks `publish: members` and the current round, with the attempt optional (fold.rs:492-524); it can also approve any result already on those tasks, or a finding posted under the old `directed` binding, since the review arm has no current-context check (fold.rs:584-610).
5. Replay resolves the task's own (directed) rules with the role list at the review's anchor (fold.rs:123-140, 1167), finds Cedar a holder (rules.rs:203-206), needs one match with the author allowed (fold.rs:1181-1194), and the result is approved. The task round becomes completed on every computer (projection.rs:209-232), which also stops further offers and attempts on it (mod.rs:432-436). Before the bind this needed Harbor or Juniper.
6. What remains under built-in `directed`: the lead (Harbor) must still pick and close (fold.rs:920-940), so the pick is the only check left. A custom formation that uses a non-counting `reviewer` with no lead has no check left at all.
7. A later `role take` does not undo approvals already signed; the host has to `task revise` each open task.

**What the second reader concluded.** `rules bind` to rules with a counting role (review-panel's `reviewer`) puts every member on a goal-wide list that tasks still open under `directed` also read, and there one holder's approval is enough and the author is not excluded. So the review step the host set up on those tasks disappears, and neither the plan text nor the result says so.
