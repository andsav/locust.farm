# MoltMesh security and trust-boundary review

Research date: 2026-10-03. See the [research index](README.md) and [validation report](moltmesh-validation.md) for complementary runtime evidence.

Reviewed repository: `https://github.com/sahilpohare/MoltMesh`, commit `707c870e3188df243e5aea3c4662daa3253270bc` (actor-model branch). Scope: identity/session authentication, authorization across the local API and P2P ingress, file confidentiality/materialization, webhook destinations, and related resource/trust assumptions. No applicable `AGENTS.md` was found in the checkout or checked ancestors.

This is a **read-only source review**, not a penetration test or a cryptographic audit. No exploit was generated, no daemon was targeted, and no new tests were run by this reviewer. “Confirmed” below means the described checks or missing checks are visible in the complete cited code path. Operational exploitability, deployment exposure, and impact under a particular environment remain untested. Companion reviews cover consensus/recovery and task lifecycle in greater detail.

## Assessment

There is useful engineering here: separate daemon/SDK keys, real Ed25519 challenge-response, verified signed discovery cards, recipient-scoped APIs, and an encrypted-entry verification path. The implementation nevertheless does **not** consistently provide an authorization boundary between mutually untrusted SDK clients, between arbitrary mesh peers and local thread state, or between transport identity and end-to-end agent authorship. These are stronger concerns than generic warnings about P2P networking.

For Locust, borrow the decomposition and some identity mechanics; do not inherit the authorization model unchanged. The safest coherent initial trust model is an owner-controlled local daemon with explicit invitations, fully authenticated agent interfaces, immutable artifacts, and a separate privileged administration interface.

## Things the source does correctly

- Session initiation validates that a 32-byte Ed25519 signing public key derives the claimed DID, requires a 32-byte encryption public key, creates a cryptographically random 32-byte challenge, expires it after 60 seconds, and consumes it on completion even for an invalid signature. The signature binds the daemon ID, challenge ID, nonce, expiry, and agent DID through a domain-separated payload. Tokens are random and stored in the session map by SHA-256 digest; sessions expire after 15 minutes. See [`daemon/session/session.go:20-108,195-229`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/session/session.go#L20-L108) and [signed payload / DID checks](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/session/session.go#L195-L229).
- Existing tests assert challenge replay rejection, required authentication for `GetAgentIdentity`, isolation of one agent's task from a second authenticated agent, and rejection of a legacy call while two SDK identities are active. These tests were **read, not run**. [`daemon/rpc/session_test.go:18-63`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/rpc/session_test.go#L18-L63)
- Discovery-card signatures are actually verified against the public key encoded in the DID. Expired records and excessive future timestamps are rejected; resolve additionally checks the requested DID matches the card. SDK publication checks DID, host peer ID, and encryption key against the session. [`pkg/a2avalidator/validator.go:136-160`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/pkg/a2avalidator/validator.go#L136-L160), [`daemon/registry/registry.go:119-138`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/registry/registry.go#L119-L138), [`daemon/rpc/server_registry.go:32-54`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/rpc/server_registry.go#L32-L54).
- Direct message ingress authenticates the libp2p peer, checks the claimed sender against that peer or a verified SDK card bound to it, checks the recipient is the local daemon or a currently hosted SDK identity, enforces a 4 MiB message frame bound, and uses a stream deadline. [`daemon/deliver/deliver.go:52-55,341-405`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/deliver/deliver.go#L341-L405)
- The encrypted `AppendEntry` branch checks session author, current membership, current membership/encryption epochs, signature and nonce format. Key retrieval uses the authenticated recipient DID, rather than accepting a caller-supplied recipient to fetch another member's envelope. [`daemon/rpc/server_threads.go:689-731`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/rpc/server_threads.go#L689-L731), [key retrieval:932-948](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/rpc/server_threads.go#L932-L948).
- Default daemon initialization creates the data directory with mode `0700`; the default gRPC address is a Unix socket under it. Thus absent RPC authorization is **not automatically an unauthenticated Internet exposure in the default deployment**. [`cmd/moltmesh/daemon.go:198`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/cmd/moltmesh/daemon.go#L198), [socket selection:395-418](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/cmd/moltmesh/daemon.go#L395-L418).

## S1 — A signed incoming descriptor is not bound to the existing thread owner

**Confirmed authorization gap at remote ingress; high significance.** `receiveHandlerRaw` accepts a `THREAD_INVITE` if the descriptor signature is valid and the addressed recipient appears in the supplied replica list. `VerifyDescriptor` verifies the signature against the **incoming** `CreatorDid`; it does not bind the thread ID to an existing genesis/creator. `ActorManager.InviteReceived` only compares the old and new `N` to decide whether to restart an actor, then calls `SaveThread`. The store uses `INSERT OR REPLACE` keyed by the supplied ID. No check in this path requires an existing thread's creator to authorize its replacement.

Evidence: [`daemon/deliver/deliver.go:407-438`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/deliver/deliver.go#L407-L438), [`daemon/thread/descriptor.go:36-56`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/thread/descriptor.go#L36-L56), [`daemon/thread/actor_manager.go:119-134`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/thread/actor_manager.go#L119-L134), [`daemon/thread/store_threads.go:11-21`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/thread/store_threads.go#L11-L21).

Consequence visible from source: a valid signature by a different key is sufficient to replace durable creator/replica/metadata fields for a known thread ID through this path. If the old actor remains active, the persisted descriptor and running actor can also disagree. The downstream consensus effects were not exercised.

**Locust lesson:** bind workspace/thread ID to immutable genesis authority, distinguish first admission from a subsequent update, and validate monotonic authorized membership transitions before replacing durable metadata. A signature over a newly supplied object does not authorize replacing an existing object. New unsolicited invitations should be proposals subject to local admission policy, not permission to allocate and activate arbitrary replicas.

Defensive regression case: preserve a thread's owner and state when presented with a validly signed conflicting descriptor from a different creator; also reject rollback to an older otherwise valid descriptor.

## S2 — Generic plaintext append bypasses encrypted-entry membership checks and accepts internal commands

**Confirmed source-level authorization gap; high significance for multiple agents sharing a daemon.** `AppendEntry` obtains an owner but constructs an unrestricted plaintext `ThreadEntry` from caller-supplied `Payload` and `Kind`. All membership, epoch, and author-signature checks are conditional on `req.EncryptedEntry != nil`. The plaintext path enqueues directly. `ActorManager.AppendEntry` and `Store.EnqueueEntry` have no author-membership checks.

Evidence: [`daemon/rpc/server_threads.go:676-734`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/rpc/server_threads.go#L676-L734), [`daemon/thread/actor_manager.go:141-150`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/thread/actor_manager.go#L141-L150), [`daemon/thread/store_pending.go:13-23`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/thread/store_pending.go#L13-L23).

This is more than a plaintext confidentiality exception: generic caller-controlled `Kind` can name `membership:add-observer`. The dedicated `AddThreadReplica` endpoint checks that the caller is the creator, but `raft.applyMembershipEntries` handles the same command kind and changes replica routing without checking `entry.AuthorDid`. On a creator daemon it re-signs and saves the new descriptor. The consensus reviewer separately examined the commit path.

Evidence: [dedicated creator check and command construction, `server_threads.go:64-82`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/rpc/server_threads.go#L64-L82), [state-machine command handling, `raft.go:771-800`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/thread/raft.go#L771-L800).

**Locust lesson:** separate user content from protocol control commands by type and admission interface; enforce authority in the state machine as well as the RPC. A legacy plaintext branch must not disable membership authorization. Define encryption mode per workspace and enforce it, instead of allowing the request shape to select a weaker mode.

The documentation's claim that daemon/log/archive payloads contain only ciphertext is consequently too broad: [ADR-0014:9-18](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/docs/adr/0014-encrypted-thread-payloads.md#L9-L18). There is a real encrypted path; it is not a universal invariant.

## S3 — Legacy scoping falls open according to live session count

**Confirmed isolation flaw under an untrusted-local-client or exposed-TCP threat model.** The gRPC server has only a logging unary interceptor, no shared authorization interceptor, no streaming interceptor, and no TLS options. It can listen on a configured TCP address. Authentication is handled piecemeal in methods. More importantly, `scopedOwner` accepts requests without a bearer token whenever there are zero or one active distinct SDK identities, returning the empty owner.

Evidence: [`cmd/moltmesh/daemon.go:403-418`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/cmd/moltmesh/daemon.go#L403-L418), [`daemon/rpc/server.go:114-141`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/rpc/server.go#L114-L141), [`daemon/session/session.go:177-193`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/session/session.go#L177-L193).

Empty owner means **all owners**, rather than a separate daemon-owned namespace, in inbox reads/subscriptions and outbox reads. As identities disconnect or their 15-minute sessions expire, previously stored multi-agent data becomes accessible to anonymous legacy callers. An anonymous inbox subscription admitted before a second identity joins stays a wildcard: owner is checked only at stream setup, and subsequent notifications do not re-check sessions. Normal authenticated streams similarly do not terminate on token expiry/revocation.

Evidence: [`daemon/inbox/inbox.go:75-118,122-135`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/inbox/inbox.go#L75-L135), [`daemon/outbox/outbox.go:117-143`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/outbox/outbox.go#L117-L143), [`daemon/rpc/server_messaging.go:32-70`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/rpc/server_messaging.go#L32-L70).

Related instance: `PutThreadKeyEnvelope` checks creator authorization only when `owner != ""`. The ordinary, non-recovery envelope path lacks a creator signature check and stores envelopes with `INSERT OR REPLACE`. An anonymous legacy caller with access to that API can replace another member's current envelope with data of the right shape. This demonstrates integrity/availability risk, **not** recovery of the real plaintext content key. Recovery envelopes have an additional signature check and should not be conflated with this ordinary path.

Evidence: [`daemon/rpc/server_threads.go:788-869`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/rpc/server_threads.go#L788-L869), [`daemon/thread/store_keys.go:13-27`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/thread/store_keys.go#L13-L27).

**Locust lesson:** separate OS-owner administration credentials from agent credentials. Missing agent credentials must never select a global namespace. Authenticate every RPC/stream by default; provide an explicit authenticated admin route for cross-agent operations. Specify whether a stream is leased by its session and how revocation closes it. An identity proof is not daemon admission: anyone who can reach `BeginAgentSession` can create their own key and authenticate as themselves because there is no host-issued enrollment authorization in that path.

Exposure qualification: the default `0700` directory is a useful OS boundary. TCP exposure is configuration-dependent, and TLS could be terminated externally. These facts do not repair cross-agent isolation for clients deliberately given access to one daemon.

## S4 — Some RPCs remain daemon-wide regardless of supplied session

**Confirmed authorization surface; practical impact depends on the intended local trust model.** `GetThread`, `GetThreadEntries`, and `SubscribeThread` perform no caller authentication/membership checks. Generic `Publish` and `SubscribeTopic` also have none and accept arbitrary topic names; the gossip layer validates only topic formatting and payload size. File APIs and peer connect/disconnect operations are likewise not session-authorized.

Representative evidence: [`server_threads.go:46-50`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/rpc/server_threads.go#L46-L50), [entry reads/stream:951-1006](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/rpc/server_threads.go#L951-L1006), [`ext.go:19-55`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/rpc/ext.go#L19-L55), [`gossip.go:249-256`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/gossip/gossip.go#L249-L256), [`diag.go:127-192`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/rpc/diag.go#L127-L192).

Network membership does not create a private transport channel. `Broadcast`/`SubscribeBroadcast` check a **local SQLite** membership record, then use an ordinary deterministic GossipSub topic; generic topic APIs bypass those convenience checks. Inbound generic gossip strips sender metadata before delivering raw `msg.Data`. GossipSub `StrictSign` verifies a network identity's authorship, but it does not itself establish workspace membership or confidentiality.

Evidence: [`daemon/network/network.go:1-5,260-281`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/network/network.go#L260-L281), [`daemon/gossip/gossip.go:161-195`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/gossip/gossip.go#L161-L195), [`daemon/node/node.go:123-126`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/node/node.go#L123-L126).

**Locust lesson:** retain authenticated author metadata through dispatch, reserve protocol topics, authorize reads as well as writes, and define whether ciphertext/metadata are public. Encryption may legitimately permit broad ciphertext replication, but a plaintext legacy path makes unrestricted reads materially different. A topic name is not an access-control capability.

## S5 — SDK identity separation stops at the sending daemon for ordinary messages

**Confirmed trust-model limitation, not proof a third-party peer can forge an unrelated agent.** The ordinary `Message` protobuf has a signature field and describes an encrypted payload, but the examined send/receive path does not sign or verify that field and does not perform application-layer encryption. It uses authenticated encrypted libp2p transport and, for an SDK DID, a verified card binding that agent to `NodePeerId`. That proves the sending **daemon** is a transport endpoint previously authorized in the card; it does not prove the SDK agent signed this individual message.

Evidence: [`proto/a2a.proto:91-101`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/proto/a2a.proto#L91-L101), [`daemon/rpc/server_messaging.go:12-29`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/rpc/server_messaging.go#L12-L29), [`daemon/deliver/deliver.go:330-405`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/deliver/deliver.go#L330-L405). Task result construction likewise puts plaintext serialized result bytes in `Message.Payload` and leaves the signature unset: [`server_tasks.go:309-316`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/rpc/server_tasks.go#L309-L316).

A compromised sending daemon therefore remains trusted to speak for SDK identities bound to it while their cards are accepted. Closing a local SDK session does not revoke its already published card at remote receivers. The encrypted thread-entry branch has separate author signatures and is a stronger boundary; do not generalize this message finding to those signatures.

**Locust lesson:** decide explicitly whether daemons are trusted delegates or untrusted transports. For portable agent-authored evidence, sign each semantic application event with the agent key and include workspace, recipient/scope, type, causal/input references, and replay identifiers. If daemons are delegates, make that delegation scope and validity explicit rather than inferring unlimited authorship from a routing card.

## S6 — Friendly name ownership is enforced by the client, not the DHT record rule

**Confirmed protocol authorization gap if names are used as trusted identities.** `names.Claim` checks whether an existing live claim belongs to another DID before publishing. However, `NameClaimValidator` accepts a new claim signed by whatever DID the new record names; it does not require authorization from the existing owner. Selection chooses the highest valid `PublishedAt`. The pre-check is therefore a cooperative-client policy, not an enforced ownership invariant. Querying multiple DHT peers does not strengthen a record rule that accepts a conflicting owner's self-signature.

Evidence: [`daemon/names/names.go:122-174`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/names/names.go#L122-L174), [`pkg/a2avalidator/validator.go:174-204`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/pkg/a2avalidator/validator.go#L174-L204), [`daemon/names/names.go:219-243`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/names/names.go#L219-L243).

**Locust lesson:** keep friendly names as locally pinned aliases to keys, or design an explicit namespace authority and transfer rule. Self-certifying cryptographic IDs are useful; scarce global names and Sybil-resistant reputation are a different problem. Do not treat a valid signature from a new key as authorization to reassign an existing name.

Related lower-confidence operational risk: capability index records are unsigned JSON arrays; validation only unmarshals them and selection prefers the longest list. The eventual agent cards are signed and checked for capability membership, so this does **not** forge their signatures, but untrusted indices can affect discovery work and availability. [`pkg/a2avalidator/validator.go:84-128`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/pkg/a2avalidator/validator.go#L84-L128), [`daemon/registry/registry.go:165-185,295-324`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/registry/registry.go#L165-L185).

## S7 — Webhook destination checks do not survive redirects or DNS changes

**Confirmed missing enforcement at request time; SSRF impact untested.** `validateWebhookURL` resolves the hostname at configuration time and rejects common private/internal addresses. Delivery later uses a plain `http.Client{Timeout: ...}` and `client.Do`; there is no custom `DialContext` or `CheckRedirect` policy. Thus the configured name may resolve differently at use time, and a previously permitted public endpoint can redirect to a destination that was never checked. The response body is not exposed through the RPC, so this is not automatically a read-and-return SSRF primitive.

Evidence: [`daemon/webhook/webhook.go:65-71,96-133`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/webhook/webhook.go#L65-L133), [delivery:194-234](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/webhook/webhook.go#L194-L234).

**Locust lesson:** make local/private callback authorization explicit; apply the destination policy to the resolved address actually dialed and every redirect, or disable redirects. Since this is intended to serve local agents, decide deliberately whether an operator-approved localhost callback is allowed rather than implementing an incomplete blanket prohibition. The network policy belongs to the host, not the model.

## S8 — Files are content-addressed plaintext, not automatically private shared artifacts

**Confirmed storage/API behavior; remote transfer policy covered by the networking reviewer.** `SendFile` hashes and stores `req.Data` directly and notifies Bitswap. The node instantiates Bitswap over its blockstore without a per-workspace or per-artifact authorization hook. `FetchFile` returns local blocks or fetches them by CID without a session/membership check. This differs from encrypted thread entries: calling the artifact API does not automatically encrypt a file.

Evidence: [`daemon/rpc/server_files.go:22-55,71-109`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/rpc/server_files.go#L22-L55), [fetch](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/rpc/server_files.go#L71-L109), [`daemon/node/node.go:151-156`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/node/node.go#L151-L156).

I did **not** find evidence here of automatic remote path materialization or archive extraction that would support a specific path-traversal finding. CLI fetching writes to the local caller's explicit `--out` path; Python likewise takes an explicit caller-supplied destination. These are not remote `Artifact.Name` path writes. [`cmd/moltmesh/files.go:50-86`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/cmd/moltmesh/files.go#L50-L86), [`sdk/python/moltmesh/client.py:501-510`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/sdk/python/moltmesh/client.py#L501-L510).

**Locust lesson:** encrypt before shared content-addressed storage when confidentiality is expected, distinguish authorized export from local file access, and introduce path containment checks if automatic workspace materialization is added. Hash verification provides integrity relative to a digest; it does not grant access or prove the expected author.

## S9 — Resource admission and key custody remain operator responsibilities

These are **risks and design boundaries**, not measured denial-of-service findings:

- Session maps accept any valid self-generated identity and prune only by expiry; each access iterates existing entries. There is no per-client enrollment/admission policy in `session.go:60-75,205-215`.
- A correctly addressed and self-signed unsolicited descriptor triggers persistent thread creation and actor activation (S1), rather than waiting for recipient consent. Direct task messages likewise create durable local task rows after sender identity validation. [`server_tasks.go:333-349`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/rpc/server_tasks.go#L333-L349)
- Limits exist for individual network messages and libp2p connection management; these are valuable, but they do not by themselves bound persistent workspace count, incoming task count, or bytes stored per untrusted sender. Rate/space/admission guarantees require workload tests and a documented host policy.
- Daemon identity persistence writes base64 private-key material as mode-0600 JSON, not encrypted-at-rest material. Python SDK identity is similarly plaintext key material protected by file mode; TypeScript uses unencrypted PEM. This is an OS-credential boundary, not necessarily a bug, but [ADR-0002:33-34](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/docs/adr/0002-did-key-identity.md#L33-L34) promises more. See [`daemon/identity/identity.go:59-72`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/daemon/identity/identity.go#L59-L72), [`sdk/python/moltmesh/identity.py:82-100`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/sdk/python/moltmesh/identity.py#L82-L100), [`sdk/typescript/openclaw-plugin/src/identity.ts:43-62`](https://github.com/sahilpohare/MoltMesh/blob/707c870e3188df243e5aea3c4662daa3253270bc/sdk/typescript/openclaw-plugin/src/identity.ts#L43-L62).

**Locust lesson:** keeping sandbox selection with the participant is compatible with a narrow secure daemon. The protocol still needs explicit resource admission, per-agent scoped interfaces, and keys outside agent-writable workspace/sandbox mounts. Peer messages and code remain untrusted even when signed. Do not let signatures, a self-issued session, or a content hash automatically confer execution authority.

## Priority lessons for Locust

1. Define three principals explicitly: machine owner, daemon transport, and agent. Choose which can delegate to which, with scoped signed authorization.
2. Deny missing credentials by default. Keep privileged administration on a distinct local interface; never key privacy on the number of currently active sessions.
3. Anchor every workspace to immutable genesis authority. Validate history/membership updates before durable mutation across every ingress, including invitations, gossip, recovery, and local APIs.
4. Make control commands structurally distinct from user content. Revalidate authority in the replicated state machine.
5. Use encrypted immutable artifacts with explicit exports. Keep automatic file materialization and execution out of the synchronization daemon initially.
6. Treat friendly names, routing cards, message signatures, membership, and artifact hashes as separate claims with separate validators.
7. Test transitions across boundaries: session expiry with persisted data, stream revocation, different creator/same thread ID, plaintext attempts in an encrypted workspace, generic content carrying reserved command kinds, forbidden callback redirects, and unsolicited resource allocation.

The practical conclusion is not that decentralization is inherently unsafe. It is that signed discovery and replicated storage are only parts of the protocol: **admission, authorization, state-transition validation, and execution control need their own explicit invariants.**
