# First collaboration journeys

**Status: proposed organization runtime procedures.** These journeys specify the
intended observations and approval boundaries. The offline authoring CLI cannot
create goals, admit members, publish runtime contributions or launch a harness.
No executable runtime commands are invented here.

## Two local agents

Prerequisites are two deliberately configured local profiles, independent Locust
participant/session bindings, verified tool readiness and an administrator able
to admit them. Two native chats using one enrolled profile may share one Locust
session; do not count them as independently identified participants.

1. State the goal's outcome and choose a blueprint. Open research needs no
   invented task or universal accepted code head; a reviewed patch can use a
   specialized task rule.
2. The administrator admits both identities and binds the exact definition and
   role/input values. Inspect the effective instance rather than treating a role
   name as self-asserted permission.
3. Select the exact material each participant may receive. Review the shared
   goal read boundary and separately grant local execution where appropriate.
4. One participant contributes a finding or attempts an eligible task. Inspect
   the exact artifact and provenance, not just a mutable display title.
5. The other reviews that exact contribution if the rule authorizes it. A later
   contribution does not inherit a prior review.

Expected observations are two authenticated participants, the chosen rule context,
a visible immutable contribution and its evidence/criterion status. Missing proof
is pending verification. Local inability to execute does not imply rejection of
the contribution or revoke other independently authorized work.

## Invite a person

Before sending an invitation through a channel you choose, identify the recipient,
goal, membership scope and exact selected content. Approval to configure Locust
is not approval to share. The recipient must inspect the inviter, incoming
material, destination and use of their client/account before joining.

Topics and roles do not create private channels. Membership is the initial read
boundary. Use a separate goal with separate membership for a confidential subgroup;
export only specifically approved inputs and review its returned contribution
under the parent goal's own rule. Public site pages collect no tickets or secrets.

## Share a code snapshot

Choose an exact repository base and explicitly selected files/history. Exclude
credentials and private material, then inspect the immutable snapshot identity
before export. A recipient materializes into an intentionally selected workspace;
receiving bytes neither grants execution nor changes their main checkout.

A patch contribution names its base, artifact and declared test evidence. A signed
report attributes the claim to its signer; it does not prove independent tests
ran. Review [completion](completion.md) before choosing an output and
[local patch application](apply.md) before changing a checkout.
